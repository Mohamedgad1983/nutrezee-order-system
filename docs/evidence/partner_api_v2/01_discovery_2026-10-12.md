# Partner API v2 (`/integration/*`) — discovery, 2026-10-12

Read-only probe of the extended Partner API announced by the app developer (live with the existing key).
All nine endpoints were pulled completely with `limit=500` + `next_cursor` from the VPS (root-only copies under
`/root/partner-api-probe/`, aggregates only in this document). Source: `analyze.py` there. Evidence labels:
**Verified** = measured on the pull; **Inferred** = read from the data shape; **NC** = needs the developer.

## 1. Endpoints, volumes, freshness (Verified)

| Endpoint | Rows | Pages | Pull time | Snapshot built | Notes |
|---|---|---|---|---|---|
| `/customers` | 25,556 | 52 | 54 s | 04:40 daily | addresses + subscription ids embedded |
| `/customer-addresses` | 12,436 | 25 | 23 s | 04:40 | own feed, `location_pin` |

Envelope: `{count, next_cursor, mode: "live", snapshot_built_at, server_time, data}`. Every row carries `changed_at`,
`deleted`, `deleted_at`; `?since=` is supported per the developer (not exercised here). `mode: "live"` on the production key.
Developer-stated refresh: hourly, schedule nightly — matches the `snapshot_built_at` values seen (04:40 / 03:30 Kuwait).

## 2. Keys and joins (Verified)

- `customer_ref` and `subscription_id` are the stable keys; `subscriptions.order_number` equals the legacy admin
  "Order U.No" (85/85 of the screen-report orders found by it).
- subscriptions→customers 99.7 % join; financials→subscriptions 100 %; addresses→customers 100 %.
- `customer_code` is NOT unique (7,434 distinct for 25,556 customers) — use `customer_ref`.

## 3. What each feed holds — and data-quality findings

### customers
- 25,495 active / 61 inactive; 0 deleted. Registered: 2024 6,886 · 2025 7,930 · 2026 10,279.
- phone 100 % present, 99.4 % Kuwait 8-digit; **824 duplicate phones** (same number on 2+ customer_refs — the
  "1 customer, 2 accounts" case). email 100 % present (25,539 distinct). date_of_birth 71 % (contains `0000-00-00`).
- **gender is `male` for 100 %** → field is not maintained; do not use.
- Only **37.4 % have any subscription** (9,546 customers); 16,010 registered-but-never-subscribed accounts.
  Max 132 subscriptions on one customer. 52.9 % have no address.

### customer-addresses
- 12,436 addresses, 118 areas (`area_id`, `area_en`, `area_ar`), types house 86 % / apartment 12 % / building / office.
- street 99.8 %, house_no 99.4 %, building 91.9 %, extra_directions 71 %, flat_no 0.9 %, landmark 5 %.
- **`location_pin` present on 76 %** (9,448 addresses) — this is the geo data the legacy screen scrape never had
  (see `legacy-scraper-and-geo-2026-06-26`): usable for the driver app / Fleetbase pins.
- `contact_no` is "0" on 99 % → useless; `gmap_link` always empty; `is_default` true on only 2 rows (not maintained).

### subscriptions
- status only `success` (16,535) / `cancel` (2,236) — **no pause/expired/active state; "current" must be derived from
  `end_date >= today`** (1,102 current or future today). 38 customers hold 2+ current subscriptions.
- package (7 packages, 89 sub-packages; `grams` always "0"; meals_per_day, snacks_per_day), duration (26 d 41 %,
  20 d, 13 d, 30 d, 6 d, 1 d, 3 months), `frozen_days` (0 for 87 % of current), `delivery.time_slot` (2 slots:
  "From 5 AM to 4 PM" 77 %, "Before 1 day" 23 %), `off_day_mode` friday_off 80 % / weekend_off 16 %,
  `off_weekdays`, `thursday_double_box` (98 subs), `delivery_address_id`.
- `end_date` is the **current** end: for 3 of 85 orders in the 2026-10-11 screen report the screen still showed the old
  end date while the API showed the extended one (`days_added`) — all three had already received a renewal reminder
  by mistake. The API is the better source for expiry.

### subscription-schedule
- 106,357 rows, 4,983 subscriptions, 2026-06-09 → 2027-05-28; `state` delivery 96,348 / frozen 10,009;
  `box_count` (1 for 96 k, 2 for 260, 0 on frozen days), `meal_item_count`, `total_qty`. No dish names (counts only).
- Gives per-day delivery truth (incl. frozen days) → a cleaner "days remaining" than end-date arithmetic.

### subscription-changes
- freeze 46,844 (7,796 later lifted, `is_reverted`), days_added 1,827 (`old_end_date`/`new_end_date`, 12 negative
  deltas = days removed), cancelled 2,236. 89 subscriptions got days added in the last 30 days.
- This is the renewal/extension signal the screen lacks. No price on a days_added change (NC: is it paid?).

### preferences
- 4,246 subscriptions (23 % of all): special_requests free text 99.8 %, allergies list on **0.1 %** (near-unused),
  extra_protein 3.7 %, extra_carb 5 % (grams as strings).

### financials
- One row per subscription; KWD only. amount_paid total **1,712,152 KWD** (median 96.9); 12.1 % zero amount
  (developer: valid 100 % coupons). payment_method knet 71 % / cc 20 % / apple-pay 9 %.
- coupon on 46.5 % (195 codes; percentage 98 %); promo_discount on 6 rows; consultation_fee and addons_paid are
  effectively unused; finance_status filled on 27 rows only; `gateway_captured` true 16.8 % (stored since late May 2026).
- cashback_earned filled 22.9 % (sum 23,003 KWD), redeemed 3.2 % (sum 3,970 KWD).

### payments
- 14,632 rows for 14,616 subscriptions → **≈4,150 subscriptions have no payment row** (zero-amount coupons + older
  orders; NC). status success; method knet 63 % / cc 26 % / 11.5 % blank; `tran_id` 92.7 %, `payment_id` 99.1 %,
  `ref_no` 99.4 %, `gateway_result` on 21.6 % (CAPTURED 3,156). One add-on payment exists in total.

### balances
- 3,067 customers, **cashback_balance = 0 for every one** while `cashback_earned_total` is populated → either all
  cashback is expired/redeemed or the balance field is not computed (NC with the developer).

## 4. Not available (developer statement, confirmed by the data)
No renewal record (a renewal is a new subscription or a `days_added` change); no end-date history beyond
old/new on `days_added`; no refunds; no pause state; no dish selection per day; no driver/delivery outcome.

## 5. What this enables (Inferred)
1. **Expiry report + WhatsApp reminders from the API instead of the admin screen**: exact current end date,
   frozen days, no admin password/browser, seconds instead of minutes; keep the screen as a cross-check for a week.
2. **Driver app / labels**: 9,448 address pins + structured addresses by `delivery_address_id`.
3. **Finance/BI**: per-subscription revenue, coupons, payment method, gateway capture — joinable to ERPNext by
   phone (`customer_ref` ↔ legacy phone) and to the executive dashboard.
4. **Retention**: `subscription-changes` (freezes, extensions, cancellations) + schedule gaps.

## 6. Open questions for the developer (NC)
`balances` all zero; meaning of `finance_status`; why ≈4k subscriptions lack a payment row; whether `days_added`
is paid; `gender`/`is_default`/`contact_no` unmaintained; `?since=` semantics on `subscription-schedule`
(nightly rebuild → does every row change?).
